# 改 wgpu-hal 值不值 —— 代价评估

> **结论先行：现在不改。**
> 收益是「省掉一次 GPU→GPU 拷贝」，代价是仓库背一份 **2.0 MB / 45,262 行**的第三方
> 源码，并且**每次升级 wgpu 都要重新对账**。
>
> 这次拷贝值多少已经有实测了（见 §3，原始数据 `copy-bandwidth.csv`）：
> RTX 4060 Laptop 上，4K 单页 31.6 MB 的一次拷贝是 **0.348 ms**（占 60 fps 预算 2.1%），
> 8K 双页 126.6 MB 是 **1.384 ms**（8.3%）；而视口量级（≤16 MB）只要
> **0.012–0.093 ms**（0.07%–0.56%）。
> 按 §4 写死的判据，4K 单页刚卡在 2% 边界、8K 双页落在中间档，
> **两档的动作都是「不改，先落实按需拷贝」**。
>
> 另有一条反向风险比这笔账更重要：fork 之后 wgpu 会**直接在 SHARED 堆的纹理上渲染**，
> 而 shared 堆上的渲染性能**尚未测过**（§4.1）。万一渲染变慢，省下的拷贝会被抵消。
>
> 本文给出精确的改动位置、体量数字、四种落地方式的取舍，以及一条写死的动手判据。

---

## 1. 要改的到底是什么

`wgpu-hal 27.0.4` 创建纹理时不带 `D3D12_HEAP_FLAG_SHARED`，所以
`CreateSharedHandle` 直接返回 `E_INVALIDARG (0x80070057)`。
补丁的唯一目标：**让某一张纹理建在 SHARED 堆上**。

### 1.1 两条路线，改动面都只有 1 个文件

| 路线 | 改动点 | 行数 |
|---|---|---|
| **α. 让 wgpu 自己建共享纹理** | `src/dx12/suballocation.rs`：`DeviceAllocationContext::create_texture`（221–243）命中标记时强制走 committed；`create_committed_texture`（495–501）的 heap flag 加 `\| D3D12_HEAP_FLAG_SHARED` | ~10 行 |
| **β. 我们自己建，导入 wgpu** | `src/dx12/mod.rs`：加一个 `Texture::from_raw_shared(resource, desc)` 构造函数（内部复用已存在的 `Allocation::none`），再走公开的 `Device::create_texture_from_hal`（`wgpu-27.0.1/src/api/device.rs:317`） | ~15 行 |

导出侧**两条路线都不用改**：`wgpu_hal::dx12::Texture::raw_resource()` 已经是公开的
（`src/dx12/mod.rs:936`），拿到 `&ID3D12Resource` 后自己调 `CreateSharedHandle` 即可。

β 路线额外的好处是**完全不碰 wgpu 的分配器**（共享纹理由我们按已验证的方式创建），
代价是 ownership 语义要自己讲清楚（wgpu 会在 drop 时 Release 这个资源）。

### 1.2 「只加一个 heap flag」在本机会静默失效（关键）

`src/dx12/adapter.rs:319`：

```rust
suballocation_supported: !info.name.contains("Iris(R) Xe"),
```

RTX 4060 上该值为 `true` → 纹理走 `create_placed_texture`，即**在 `gpu_allocator` 的
4 MiB–256 MiB 大块里做子分配**（`suballocation.rs` 里 `gpu_allocator::d3d12::Allocator`），
而不是 `CreateCommittedResource`。

placed 资源**自身不携带 heap flag**，能不能共享取决于它所在的堆，而 `gpu_allocator`
建的堆不带 `SHARED`。所以：

> 只改 `create_committed_texture` 的 heap flag，在这台机器上**根本不会被走到**，
> 现象是「补丁打了、热测没变化」，极易误判为「补丁无效 / SHARED 不可行」。

真正要改的是 α 路线的**两处**：命中标记时强制 committed **且** 带 SHARED。
（把整个 allocator 的堆都建成 SHARED 是反方向：等于把一大块无关显存整体暴露给 Flutter 的
设备，而且 4 MiB 起步的粒度让每张共享纹理都极浪费，不要走。）

### 1.3 「哪张纹理要共享」怎么传进去

| 做法 | 改动面 | 代价 |
|---|---|---|
| 按 `desc.label` 约定（如 `label == Some("rossi-shareable")`） | 1 crate / 1 文件 / ~10 行 | 隐式约定，可读性差；但 label 已由 wgpu-core 原样透传到 hal，**零 API 变更** |
| 环境变量全局开关 | 1 文件 / 几行 | **所有**纹理变 committed，丢掉子分配 → 显存占用与碎片行为全面改变，测出来的渲染数据不可信 |
| 真正的 API 扩展（`TextureDescriptor` 加字段 / `TextureUses` 加 bit） | wgpu-types + wgpu-core + wgpu-hal **三个** crate | 要同时 vendor 三个 crate，diff 几十行，还有与上游 API 打架的风险 |

研究性验证走 label 约定；真要提上游才走第三条。

## 2. 工程体量（实测）

`wgpu-hal-27.0.4`，本机 cargo registry：

| 项 | 数值 |
|---|---|
| 整个 crate | **2.0 MB** |
| `.rs` 文件数 | **65** |
| 全部源码行数 | **45,262 行** |
| `src/dx12`（唯一相关的后端） | **400 KB / 9,985 行** |
| `src/vulkan` / `src/gles` / `src/metal` | 472 KB / 436 KB / 248 KB（我们一个都用不到，但仍在树里） |
| `src/auxil` / `src/dynamic` / `src/noop` | 56 KB / 76 KB / 32 KB |

关键点：**cargo 的 `[patch.crates-io]` 粒度是整个 crate，不能只补一个文件。**
所以「改 10 行」在物理上必然等于「仓库里多一份 45,262 行 / 2 MB」。

### 2.1 四种落地方式

| 方式 | 仓库增量 | 代价 |
|---|---|---|
| **A. vendor 进仓并提交** | +2 MB / ~70 文件 | 研究分支被第三方源码淹没，`git diff` 失去可读性，评审时看不出我们改了什么 |
| **B. vendor + `.patch` + 脚本，目录 gitignore** | +`.patch`（~30 行）+ 脚本（~80 行） | **每次 clone 后、构建前都要先跑一次脚本**；换机器 / 升 cargo 都要重来 |
| **C. fork 到 `HibernalGlow`，`[patch] git = ...` + 锁 rev** | 0 | 多一个需要长期维护的 fork 和一条网络依赖；Cargo.lock 锁 rev |
| **D. 提上游 PR** | 0 | 时间不可控，wgpu 27 期 API 仍在变，接受度未知 |

**如果将来真要动**：自验用 B，长期用 C。

## 3. 省下来的那次拷贝值多少（实测）

上一版这里是估算（按 ~250 GB/s 保守带宽 + 视口尺寸假设）。现在有实测了：
`poc/texture-bridge/rust/wgpu-probe/src/bench.rs`，用
`cargo run --release --bin bench` 跑，原始数据落在 `copy-bandwidth.csv`。

口径：GPU timestamp 测单次 `CopyResource` 在 GPU 时间线上的**独占时长**，
源纹理由 wgpu 渲染生成，**不掺墙钟、不受刷新率影响**。

### 3.1 两个把数字测歪的坑

前一版估算避开了它们，但真去测的时候很容易踩，而且症状都表现为"结果好得不像话"：

| 坑 | 现象 | 处理 |
|---|---|---|
| **显存压缩** | 源纹理未写入（全零）时量到 363–432 GB/s，**超出这块卡 256 GB/s 的标称带宽 40% 以上** | 源纹理改由 wgpu 渲染整数 hash 噪声。漫画页是扫描件/照片，本来就高熵、不可压缩 |
| **L2 缓存** | 2.3 MB（PoC 视口）量到 444 GB/s —— 它整个放得进 32 MB 的 L2，读根本没走显存 | 判断 Gate A 只看 ≥32 MB 那几档 |

另外还有一条纯工程坑：帧循环里的拷贝被 vsync 锁死（本机 160 Hz），一帧只拷
2.5 MB，反推出的"带宽"是被刷新率封顶的假数。所以基准必须**离屏批量跑**，
不能拿帧率换算。

### 3.2 实测数据

RTX 4060 Laptop（128-bit GDDR6，标称 256 GB/s，实测拷贝吞吐约 190 GB/s ≈ 74%，属正常范围）。
数字取 `shared` 组 —— 共享堆 + 完整 barrier 往返，即真实路径：

| 尺寸 | 单张 | 单次拷贝 | 读+写吞吐 | 占 16.7 ms | 占 6.9 ms |
|---|---|---|---|---|---|
| 1264 × 487（PoC 视口） | 2.3 MB | **0.012 ms** | 403 GB/s（L2 内） | 0.07% | 0.18% |
| 1920 × 1080 | 7.9 MB | **0.033 ms** | 498 GB/s（L2 内） | 0.20% | 0.48% |
| 2048 × 2048 | 16.0 MB | **0.093 ms** | 353 GB/s（部分 L2） | 0.56% | 1.34% |
| **3840 × 2160（4K 单页）** | 31.6 MB | **0.348 ms** | 191 GB/s | **2.1%** | **5.0%** |
| 3840 × 4320（4K 双页） | 63.3 MB | **0.701 ms** | 186 GB/s | 4.2% | 10.1% |
| 4000 × 6000（24MP） | 91.6 MB | **1.002 ms** | 187 GB/s | 6.0% | 14.4% |
| **7680 × 4320（8K 双页）** | 126.6 MB | **1.384 ms** | 181 GB/s | **8.3%** | **19.9%** |
| 8000 × 12000（96MP） | 366.2 MB | **4.094 ms** | 184 GB/s | 24.6% | 59.0% |

线性度很好：≥32 MB 之后稳定在 181–191 GB/s，说明瓶颈就是显存带宽本身，
没有额外的隐藏开销。≤16 MB 靠 L2，便宜得多。

### 3.3 两个反直觉的负结论

补丁的动机之一是绕开 barrier（`RENDER_TARGET ⇄ COPY_SOURCE` /
`COMMON ⇄ COPY_DEST`）—— 直觉上 barrier 会让 GPU 停等，**有可能比拷贝本身还贵**。实测：

| 对照 | 结果 |
|---|---|
| dst barrier 的成本（`shared − nobar`） | **−6% ~ +2%**，无系统性成本 |
| SHARED 堆标志的成本（`shared − plain`） | **−20% ~ +0%**，默认堆反而略慢 |

两个曾被当作"隐性大头"的东西都不存在。**为绕开 barrier 或堆标志去改架构，没有收益。**

（大尺寸下含 barrier 反而略快，是测量抖动，不是真实效应 —— 差异都在 ±6% 内且不成趋势。）

### 3.4 三条推论

1. **按视口算（≤16 MB），拷贝成本在 0.07%–0.56%** —— 比动手门槛低一个数量级，
   而且这一段基本走 L2，是"几乎免费"的。
2. **按整页大图算，4K 单页 2.1%、8K 双页 8.3%** —— 这才是需要考虑的量级。
   但这类尺寸**不该每帧拷**：只有内容变化（翻页 / 缩放 / 超分输出更新）时才拷，
   1.38 ms 摊到一次翻页上用户感知不到。
   **「copy 按需而非每帧」这个实现约束，比「零拷贝」更值得先落地。**
3. **打了补丁也不省这些** —— `README.md` §5.3 的「引擎每帧重新打开一次 handle」、
   跨 D3D11/D3D12 设备的同步开销，在零拷贝路径上一分不少地存在。
   补丁只干掉一次 blit，不解决这条链上任何其他成本。

## 4. 动手判据（写死，避免反复摇摆）

探针里已经埋了 GPU timestamp（`window_copy_ms_*` / `window_render_ms_*`），
另有离屏基准 `bench.rs` 可跑任意尺寸。用**实测**的 `copyGPU / 帧预算` 判：

| 实测占比 | 动作 | 本机实测落在哪 |
|---|---|---|
| **< 2%** | **不改。** 把结论写进 Gate A 记录并封存这条线 | 视口量级全部落在这里（0.07%–0.56%） |
| 2% ~ 10% | 不改。先把「copy 只在内容变化时发生」落实，再复测 | **4K 单页 2.1%、4K 双页 4.2%、8K 双页 8.3%** |
| **> 10%** 且确认 copy 是真瓶颈 | 才启动 B/C 方案，先做 α 路线的最小验证（强制 committed + SHARED） | 96MP 整页**每帧**拷（24.6%）—— 但正常不会这样用 |

**当前判定：不改。** 4K 单页正好卡在 2% 边界，8K 双页落在中间档，
按表两档的动作都是「不改，先把按需拷贝落实」。

### 4.1 如果将来要重新评估，先补这个测量

fork 之后 wgpu 会**直接在 SHARED 堆的纹理上渲染**，而不是渲染完再拷一次。
但 **shared 堆上的渲染性能尚未测过**。这是本评估里唯一未验证的反向风险：
如果 shared heap 上的渲染（或 wgpu 对 committed 资源的状态管理）比普通堆慢，
省下的那次拷贝会被抵消，甚至净亏。

要补的实测：同一张 4K 纹理，分别在普通堆和 SHARED 堆上跑同样的渲染负载，
比 GPU timestamp。**这一步没做之前，任何「fork 一定更快」的说法都不成立。**

在此之前，**拷贝不是 Gate A 的未决项**：它已满足「不发生 GPU→CPU→GPU 往返」这条硬指标，
而且是纯 GPU 侧、可记账的成本。Gate A 真正的未决项是
**Release 构建下的性能量化**（见 `README.md` §7）。
