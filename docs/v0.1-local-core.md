# v0.1 本地核心（`rust/local_core/`）

> v0.1 的第一块可编译、可测试的落地代码。判据 A（三种本地来源都能读到最后一页）的宿主。
>
> 决策依据：ADR-0011（读取模型）、ADR-0005 / 0007（复用形态）、`docs/v0.1_acceptance.md`（验收口径）。

## 1. 这一层是什么

只做一件事：**把一个本地来源打开成有序的页序列，并能按页取出字节或像素。**

```text
LocalSource::open(path)
  ├── 散图文件夹        folder_source
  ├── CBZ / ZIP         zip_source
  └── CBR / RAR         rar_source   ← 逐条目按需读，不落盘
        ↓
  Vec<PageEntry>（自然序）
        ↓
  page_bytes(i) → decode::decode_rgba(i) → PagePixels { width, height, rgba }
```

公开入口只有 `LocalSource` 一个结构体加它的方法；`open` 之后它只保存
**根路径 + 来源类型 + 页序列**，不保存任何打开的文件或归档对象。

## 2. 为什么单独开一个 crate，而不是塞进 `windcore`

`rust/` 现在是 workspace：

```text
rust/
├── Cargo.toml                 ← 既是 windcore 的包清单，也是 workspace 根
│                                 （members = ["local_core"]，default-members = ["."]）
├── local_core/                ← 新增：纯逻辑，无 FRB、无 tokio、无 reqwest
└── src/                       ← windcore（FRB crate，保持不动）
```

三点理由：

1. **测试循环**。`cargo test -p rossi_local_core` 只编译这一棵树；windcore 的
   reqwest / tokio / rquickjs 都不参与。归档直读这种「有真实夹具才敢改」的代码，
   测试循环的长度直接决定改动速度。
2. **边界**。这一层不认识 FRB，也不认识 wgpu。判据 D（连读三本内存不增长）因此是
   这一层的**结构性事实**——「不持有句柄」是类型上的事实，不是某处代码记得别存。
3. **不改变既有构建语义**。`default-members = ["."]` 保证任何 `cargo build`
   （包括 Flutter 侧的 native-assets 钩子与 FRB）仍然只构建 windcore，
   新增成员不会把依赖带进发布产物。

> `hook/build.dart`、`flutter_rust_bridge.yaml`（`rust_root: rust/`）与各平台工程
> 都按「`rust/Cargo.toml` 就是 windcore」定位。所以采用**根包 + 显式 default-members**，
> 而不是把 windcore 挪进 `rust/windcore/`——后者要同时改上面三处，风险不对等。

## 3. 三种来源，三种句柄

`Locator` 没有统一成「一个字符串」，因为三种来源的最优句柄本来就不同：

| 来源 | 句柄 | 理由 |
|---|---|---|
| 文件夹 | 相对路径（`/` 分隔） | 就是它在磁盘上的身份 |
| CBZ / ZIP | **中央目录下标** | O(1) 寻址；且同名条目各自可寻址 |
| CBR / RAR | 归档内条目名（已规范化、去重） | `unrar` 的顺序扫描 API 只能按名匹配 |

ZIP 用下标是**对 mImageViewer 的有意偏离**：它用去重后的名字当句柄、读的时候重扫一遍
按名查找。同名条目在归档里是合法的（我们有一条测试专门造这个 case），用名字寻址会读错那一条；
而去重命名本来就是**为了 UI 显示**，不该承担寻址职责。

两者共同的一点：**每次读一页都重新打开归档**，不常驻句柄。代价是重复解析中央目录
（典型漫画包几百条、几 KB），换来的是判据 D 不依赖任何缓存淘汰策略是否写对。

## 4. RAR 的读取模型（ADR-0011 的落地形态）

`rar_source::read_entry` 就是 ADR-0011 写死的那条路径，逐行对应
`mImageViewer/src/rar_loader.rs`：

```text
open_for_processing()
  loop:
    read_header()  ── 命中条目 → read()   → Vec<u8> 直接进内存
                   └─ 未命中   → skip()   → 推进到下一条目
  函数返回即释放句柄
```

- **不落盘、不建 session、不跨调用持有归档对象。**
- 缓存**只存判定结果**（key = `path + len + mtime`，容量 32），不缓存内容或句柄。
- 分卷解析也单独缓存（容量 128，条目只有两个路径加一个小枚举）。
- 判定依据是**头部信息**（`volume_info()`），不是文件名——
  `Vol.2a.rar` 这种名字看起来像后续卷，实际可能是独立归档，猜文件名一定会错。
  上游检出的 `testdata/archives/rar-multipart-filename-regression/` 就是为这类误判准备的样本，
  我们的测试直接拿它对表。

### 4.1 拒绝直读的三种情况

| 判定 | 处置 | 为什么 |
|---|---|---|
| `Direct` | 直读 | 非固实、未加密、无嵌套 |
| `Solid` | **报错** `UnsupportedSource::RarSolid` | 读第 N 页要解压前 N-1 页，代价随页数平方增长 |
| `NestedArchive` | **报错** `RarNestedArchive` | 内层必须先落地成路径才能打开，v0.1 不实现嵌套 |
| `Encrypted` | **报错** `RarEncrypted` | 没有密码输入路径 |

报错用**类型**（`UnsupportedSource`）而不是错误字符串，因为 UI 要按类别给不同提示：
「这本是固实压缩的 RAR」和「这文件损坏了」不是一回事。

这也是「拒绝解压兜底」的直接后果：Rossi 手里没有第二条路，所以静默降级只会在
别处变成更难懂的失败。判定顺序（solid > nested > encrypted）与上游一致。

## 5. 页序

取规则于 mImageViewer 的 `archive_converter` / `filename_sort`，但**去掉了它对 Windows
`LCMapStringEx` 的依赖**——那套排序键只在 Windows 上存在，而 Rossi 要三平台同序。
这里改成纯 Rust 的自然序：数字段按数值比较，于是 `page2 < page10`；数值相同时用原始
字符串做确定性 tiebreak（`01.jpg` 与 `1.jpg` 不会因排序稳定性而抖动）。

顺带收紧了一处：**只有本 crate 真能解码的扩展名才算页面**（`jpg/jpeg/png/webp/bmp/gif/tif/tiff`，
与 `Cargo.toml` 里 `image` 的 feature 集严格对齐）。mImageViewer 的表更长
（`heic` / `jxl` / 相机 RAW），但那些走它的 WIC 路径，不属于 v0.1。
列了却解不了，就是让用户在读到那一页时才失败。

## 6. 文件夹来源的两步策略

1. **平铺**：只列直接子文件。这是「一个文件夹就是一本书」的常见形态，也最便宜。
2. 平铺结果为空时才**递归**：因为「书籍目录 / 章节目录 / 页」同样常见，
   而它和第 1 步的判定信号互斥（有直接子文件就说明不是章节结构）。

不跟随符号链接（用 `file_type()` 而非 `metadata()`），所以既避免目录环，
也避免「一本书的页散落在链接外的磁盘上」这种让验收口径失控的情况。
递归深度上限 8 层、总文件数上限 20000，**超限直接报错而不是截断**——
截断看起来像成功了，比报错更糟。

## 7. 怎么验证

```bash
cd rust

# 单元测试（夹具就地生成，不依赖仓库里的二进制样本）
cargo test -p rossi_local_core

# 归档直读探针：不开 Flutter、不开 GPU
cargo run -p rossi_local_core --bin local_probe -- <路径> [--repeat N]
```

探针输出：来源类型、页数、页序首尾、RAR 判定，以及**首/1/4/中/3/4/末五页的
读取与解码耗时**。

最后那一列就是 `v0.1_acceptance.md` §4.3「未测项」的量具：

> 非固实归档下 `skip()` 的实际开销（libunrar 是走 seek 还是走解压）。

**读第 N 页的耗时随 N 的增长形态**直接回答了这个问题：近似常量 ⇒ 走 seek；
线性增长 ⇒ 走解压。同一份输出也顺带把「整章落盘」那条被否决的路线放在同一把尺子上。

## 9. 接进 App（FRB 会话层，已实现于 `rust/src/api/local.rs`）

`LocalSource` 只保存路径与页元数据，所以「Reader session」由 Rossi 侧持有
（`START_WORK.md` §3.2）是自然的：在 windcore 里放一张 `id → LocalSource` 的表，
FRB 暴露下面这组函数，`local_close` 时释放。

```text
open_local_source(path) -> LocalSourceOpenResult { source | rejection }
local_source_pages(id)  -> Vec<LocalPageInfo>      // index / name / size
local_page_bytes(id, i) -> Vec<u8>                 // 该页的**编码字节**
local_close(id)         -> bool
local_open_session_count() -> u32                  // 判据 D 的探针
local_close_all()       -> u32
```

两处实现上的取舍：

1. **`open` 不用 `anyhow::Result`，改用 `LocalSourceOpenResult`。**
   本节开头那条「报错用类型不用字符串」在跨 FRB 时会被打回原形 —— `anyhow::Error`
   过桥后只剩 Dart 侧 `AnyhowException.message` 一个字符串。所以 open 的返回值里
   带一个 `LocalRejectionKind` 枚举（`UnknownFormat` / `RarSolid` / `RarNestedArchive` /
   `RarEncrypted` / `NotFound` / `Io`），类别信息以枚举过桥。
   其余接口（读字节等）的失败确实是意料之外的 IO / 损坏，继续用 `anyhow` 不会丢信息。

   注意 `LocalSource::open` 内部用 `with_context` 包了一层，所以分类要靠
   `downcast_ref` **向下穿透**，只看最外层消息会全部退化成 `Io`。

2. **`local_page_bytes` 传的是编码字节，不是像素。** 这与 ROADMAP「明确不做」里
   「不把所有图片转成 Dart `Uint8List` 再交给 Flutter」不冲突：那条禁止的是把
   **解码后的 RGBA** 搬过桥。上屏的目标形态是 Rust 侧解码后直接进 GPU texture
   （Phase 1 的 `texture-bridge`）；编码字节过桥只用于 Dart 侧兜底显示与尺寸探测。

会话表只存路径与页元数据，**体积与「打开了几本」成正比、与「读了多少页」无关** ——
这是判据 D 在 App 层仍然成立的原因，`local_open_session_count()` 就是它的量具。

判据 B/C/D 的测量都要求 Release 构建 + 真实内容，所以接线之后的第一件事是
`docs/windows-build/BASELINE.md` 那套口径下的真实漫画实测。
