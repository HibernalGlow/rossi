# v0.1 本地核心（`rust/local_core/`）

> v0.1 的第一块可编译、可测试的落地代码。判据 A（三种本地来源都能读到最后一页）的宿主。
>
> 决策依据：ADR-0011（读取模型）、ADR-0005 / 0007（复用形态）、`docs/v0.1_acceptance.md`（验收口径）。

## 1. 这一层是什么

只做一件事：**把一个本地来源打开成有序的页序列，并能按页取出字节或像素。**

```text
LocalSource::open(path)
  ├── 散图文件夹        folder_source
  ├── CBZ / ZIP         zip_source
  └── CBR / RAR         rar_source   ← 逐条目按需读，不落盘
        ↓
  Vec<PageEntry>（自然序）
        ↓
  page_bytes(i) → decode::decode_rgba(i) → PagePixels { width, height, rgba }
```

公开入口只有 `LocalSource` 一个结构体加它的方法；`open` 之后它只保存
**根路径 + 来源类型 + 页序列**，不保存任何打开的文件或归档对象。

## 2. 为什么单独开一个 crate，而不是塞进 `windcore`

`rust/` 现在是 workspace：

```text
rust/
├── Cargo.toml                 ← 既是 windcore 的包清单，也是 workspace 根
│                                 （members = ["local_core"]，default-members = ["."]）
├── local_core/                ← 新增：纯逻辑，无 FRB、无 tokio、无 reqwest
└── src/                       ← windcore（FRB crate，保持不动）
```

三点理由：

1. **测试循环**。`cargo test -p rossi_local_core` 只编译这一棵树；windcore 的
   reqwest / tokio / rquickjs 都不参与。归档直读这种「有真实夹具才敢改」的代码，
   测试循环的长度直接决定改动速度。
2. **边界**。这一层不认识 FRB，也不认识 wgpu。判据 D（连读三本内存不增长）因此是
   这一层的**结构性事实**——「不持有句柄」是类型上的事实，不是某处代码记得别存。
3. **不改变既有构建语义**。`default-members = ["."]` 保证任何 `cargo build`
   （包括 Flutter 侧的 native-assets 钩子与 FRB）仍然只构建 windcore，
   新增成员不会把依赖带进发布产物。

> `hook/build.dart`、`flutter_rust_bridge.yaml`（`rust_root: rust/`）与各平台工程
> 都按「`rust/Cargo.toml` 就是 windcore」定位。所以采用**根包 + 显式 default-members**，
> 而不是把 windcore 挪进 `rust/windcore/`——后者要同时改上面三处，风险不对等。

## 3. 三种来源，三种句柄

`Locator` 没有统一成「一个字符串」，因为三种来源的最优句柄本来就不同：

| 来源 | 句柄 | 理由 |
|---|---|---|
| 文件夹 | 相对路径（`/` 分隔） | 就是它在磁盘上的身份 |
| CBZ / ZIP | **中央目录下标** | O(1) 寻址；且同名条目各自可寻址 |
| CBR / RAR | 归档内条目名（已规范化、去重） | `unrar` 的顺序扫描 API 只能按名匹配 |

ZIP 用下标是**对 mImageViewer 的有意偏离**：它用去重后的名字当句柄、读的时候重扫一遍
按名查找。同名条目在归档里是合法的（我们有一条测试专门造这个 case），用名字寻址会读错那一条；
而去重命名本来就是**为了 UI 显示**，不该承担寻址职责。

两者共同的一点：**每次读一页都重新打开归档**，不常驻句柄。代价是重复解析中央目录
（典型漫画包几百条、几 KB），换来的是判据 D 不依赖任何缓存淘汰策略是否写对。

## 4. RAR 的读取模型（ADR-0011 的落地形态）

`rar_source::read_entry` 就是 ADR-0011 写死的那条路径，逐行对应
`mImageViewer/src/rar_loader.rs`：

```text
open_for_processing()
  loop:
    read_header()  ── 命中条目 → read()   → Vec<u8> 直接进内存
                   └─ 未命中   → skip()   → 推进到下一条目
  函数返回即释放句柄
```

- **不落盘、不建 session、不跨调用持有归档对象。**
- 缓存**只存判定结果**（key = `path + len + mtime`，容量 32），不缓存内容或句柄。
- 分卷解析也单独缓存（容量 128，条目只有两个路径加一个小枚举）。
- 判定依据是**头部信息**（`volume_info()`），不是文件名——
  `Vol.2a.rar` 这种名字看起来像后续卷，实际可能是独立归档，猜文件名一定会错。
  上游检出的 `testdata/archives/rar-multipart-filename-regression/` 就是为这类误判准备的样本，
  我们的测试直接拿它对表。

### 4.1 拒绝直读的三种情况

| 判定 | 处置 | 为什么 |
|---|---|---|
| `Direct` | 直读 | 非固实、未加密、无嵌套 |
| `Solid` | **报错** `UnsupportedSource::RarSolid` | 读第 N 页要解压前 N-1 页，代价随页数平方增长 |
| `NestedArchive` | **报错** `RarNestedArchive` | 内层必须先落地成路径才能打开，v0.1 不实现嵌套 |
| `Encrypted` | **报错** `RarEncrypted` | 没有密码输入路径 |

报错用**类型**（`UnsupportedSource`）而不是错误字符串，因为 UI 要按类别给不同提示：
「这本是固实压缩的 RAR」和「这文件损坏了」不是一回事。

这也是「拒绝解压兜底」的直接后果：Rossi 手里没有第二条路，所以静默降级只会在
别处变成更难懂的失败。判定顺序（solid > nested > encrypted）与上游一致。

## 5. 页序

取规则于 mImageViewer 的 `archive_converter` / `filename_sort`，但**去掉了它对 Windows
`LCMapStringEx` 的依赖**——那套排序键只在 Windows 上存在，而 Rossi 要三平台同序。
这里改成纯 Rust 的自然序：数字段按数值比较，于是 `page2 < page10`；数值相同时用原始
字符串做确定性 tiebreak（`01.jpg` 与 `1.jpg` 不会因排序稳定性而抖动）。

顺带把「哪些扩展名算一页」和「谁来解码」拆成了两件事。早先把它们合成一条线
（**只有本 crate 真能解的扩展名才算页**），后果是用户直接撞上「打开 zip 没反应」：

> `E:\1Hub\EH\G44 不会受伤 - NO.119 碧蓝档案 和纱 [30P-421MB].zip` 里 30 张**全是 `.avif`**
> （条目名还是 GBK，Stored 无压缩），于是归档被枚举成 **0 页**。
> UI 收到「0 页 + 无拒绝原因」，既没有页也没有解释，
> 症状落在用户身上就是「打开 zip 崩了 / 没反应」。

所以现在是两档（`page_order.rs`）：

| 档 | 扩展名 | `decode_rgba` | 谁能显示 |
|---|---|---|---|
| `Core` | `jpg` `jpeg` `png` `webp` `bmp` `gif` `tif` `tiff` `avif` | 能解 | Rust，可进 Phase 1 的 GPU 上屏路径 |
| `ShellOnly` | `jxl` `heic` `heif` | **明确拒绝**（`ShellOnlyFormat`） | 交给外壳；**解得动与否取决于平台**，见 §5.1 |

两档都算页（`is_image_name`）；`decode_support()` / `needs_shell_decoder()` 回答归属，
`LocalSource::page_decode_support(index)` 是它在会话层的出口。
**「算不算一页」是格式识别问题，「谁解得动」是解码能力问题**，把后者当前者的门槛，
症状就会落在用户身上 —— 这条是这次修复的全部理由。

`avif` 是后来从下一档搬上来的：实测发现「交给外壳」在 Windows 上等于「看不到」，
而 dav1d 能解（见 §5.2）。它现在由一个 `avif` feature 控制（默认开），
关掉即退回 `ShellOnly`，给没有 dav1d 的构建机留一条不阻塞的路。

### 5.1 「交给外壳」不等于「外壳解得动」（一次教训）

修复时我拿 `ui.instantiateImageCodec` 把样本解成了 5464×8192，据此写下
「avif 走 Dart 兜底显示路径」——**这个结论是错的**，而且错得很隐蔽：

**`flutter test` 跑的是 `flutter_tester.exe`，App 跑的是 `flutter_windows.dll`，
两者的解码器不是同一个。** 同一个文件、同一批字节，一个全过、一个全败。

真机引擎上的实测（`integration_test/avif_decode_probe_test.dart`，
样本 `.workbuddy/tmp/*.avif`，对照组是同尺寸 JPEG）：

| 样本 | 裸解码 | `ResizeImage`（显示路径实际走的） | 只读描述子 |
|---|---|---|---|
| `sample-1/2/3.avif`（5464×8192 / 5208×7808） | 失败 | 失败 | **成功，尺寸正确** |
| `c420.avif`（AV1 profile 0，4:2:0） | 失败 | 失败 | 成功 |
| `c444.avif`（AV1 profile 1，4:4:4，与 c420 同尺寸同 8bit） | 失败 | 失败 | 成功 |
| `control-large.jpg`（5208×7808） | 成功 | 成功 | 成功 |

失败一律是 `Exception: Could not decompress image.`。要点三条：

1. **不是 profile 问题**：自造的普通 4:2:0 一样解不了。
2. **不是大图问题**：同尺寸 JPEG 完全正常。
3. **是最刺眼的「半能」**：读得出尺寸、给不出像素 —— 说明格式能被识别，
   缺的是真正的 AV1 解码器。引擎 PDB（`flutter_windows.dll.pdb`）里只有
   `jpeg` / `png` / `wuffs` / `libwebp` 的符号，**`dav1d` / `libavif` / `aom` / `avif`
   一个都没有**。关掉 Impeller 重测（`FLUTTER_ENGINE_SWITCHES=1
   FLUTTER_ENGINE_SWITCH_1=enable-impeller=false`）结果不变。

所以「交给外壳」这一档的准确含义是：**本 crate 不解，而外壳解得动与否取决于平台。**
列出来的价值是用户能看见「书里有 N 页」，不是「能显示」。

**教训比结论重要**：当时我把它写成了「avif 走 Dart 兜底显示路径」，而那是拿
`flutter_tester` 的结论去套 App —— **判据的宿主必须和结论的宿主一致**。
这条对以后每一次「某格式能不能显示」的评估都适用。

仍留在 `ShellOnly` 的 `jxl` / `heic` / `heif` 就是这个状态。探针把这类页标成
`shell-only`，解码失败写成「内核不解（预期，非故障）」，免得读日志的人去追一个不存在的 bug。

### 5.2 avif 后来的解法：dav1d（连带两条新依赖）

avif 没有留在 §5.1 那个状态，因为实测发现**它本可以自己解**。三条路都量过：

| 路 | 实现 | 5464×8192 | 5208×7808（4:2:0 / 4:4:4） | 结论 |
|---|---|---|---|---|
| Rust + dav1d | `image` 的 `avif-native`（dav1d + mp4parse） | **304 ms** | 176 / 250 ms | **采用** |
| Windows WIC | `vendor/mimageviewer` 的 `wic_decoder` | 442 ms | 162 / 203 ms | 平台锁定，不采用 |
| 外壳 | Flutter 引擎 | 失败 | 失败 | —— |

Rust 侧探针（debug profile）复核：5464×8192 解码 281–318 ms、读页 2.7–14.3 ms。
**与 JPEG 同量级**，而且这个后端支持 4:4:4（这批归档正是 AV1 profile 1）。
选它而不是 WIC，除了 WIC 更慢，更因为它把能力绑死在「系统装了 AV1 视频扩展」上。

**两条代价，写清楚免得后来人踩：**

1. **构建时** —— `dav1d-sys` 经 pkg-config 找 dav1d。本机走的是 vcpkg 的 `x64-windows`
   （见 `docs/windows-build/README.md` §7.7）；macOS `brew install dav1d`，Linux `apt install libdav1d-dev`。
   **注意 Cargo 的 feature 合并**：`windcore` 依赖的是同一份 `image 0.25.10`，
   所以打开 `avif` 之后，**Flutter App 的 Rust 侧构建同样需要 dav1d**。
   要给没有 dav1d 的环境留退路，写 `rossi_local_core = { path = ..., default-features = false }`。
   另有一个反直觉的坑：**在 shell 里 export `PKG_CONFIG_PATH` 传不进去** —— Flutter 跑
   native assets 的 hook 时子进程环境是干净的（实测 `CARGO_HOME` 都没继承）。所以这条
   通道走 Cargo 的 `[env]` 段（`win-baseline-env.sh` 生成 `<repo>/.cargo/config.toml`，
   不入库）。细节与排障手法见 `docs/windows-build/README.md` §7.7。
2. **运行时** —— dav1d 是**动态库**，`dav1d.dll` 必须与 `zephyr.exe` 同目录，
   否则 `windcore.dll` 加载失败，表现是 **App 直接起不来**（不是「avif 解不开」）。
   `windows/CMakeLists.txt` 按构建环境给的 `DAV1D_DLL` 把它装进 bundle
   （`win-baseline-env.sh` 负责探测并 export）。dav1d 是 BSD-2-Clause，可自由分发。

**没走完的那条**：`dav1d-sys` 有 `build_from_src` 自编译路径（meson + ninja + nasm，能出静态库），
本机试过一次没成 —— meson 会从 PATH 里把 `sccache.EXE` 当成编译器启动器，
报 `Could not determine vs dep dependency prefix string`，于是 `build.ninja` 根本没生成。
这不阻塞：动态依赖可接受，自编译只影响「仓库自包含」这一条。
将来要做的话，突破口是把 sccache 移出 PATH（不是参数能绕开的）。

调试页现在两条路可对照：`解码器：自动 / Rust / 外壳`（默认自动 = Rust 优先，
Rust 明确回答「归外壳」时才退回引擎）。会话层的入口是 `local_page_pixels`。
**它是过渡形态**：RGBA 整块过桥，Phase 1 的 GPU texture 上屏才是终点，
别拿这一形态的耗时当判据 C 的结论。

### 5.3 瓶颈不在解码，在搬运（2026-09-16）

调试页先量到「第 16 页：解码 1526.8 ms、上屏 3887.9 ms、合计 5414.6 ms」。
在动手之前先用 `bin/scale_probe.rs` 把这一段拆成单价
（5464×8192 的 AVIF，全尺寸位图 170.8 MB）：

| 档位 | dav1d 解码 | `to_rgba8` 装箱 | 降采样 | Rust 侧合计 | 位图 |
|---|---|---|---|---|---|
| 全尺寸 | 248.9 ms | 18.0 ms | 0 | **266.9 ms** | 170.8 MB |
| `thumbnail` → 1440 | 248.9 ms | 1.3 ms | 76.6 ms | **326.7 ms** | 11.9 MB |
| `thumbnail` → 768 | 248.9 ms | 0.4 ms | 55.6 ms | **304.8 ms** | 3.4 MB |

**Rust 侧全尺寸只要 267 ms，而 App 里同一页量到 1526 ms** —— 差的 1260 ms
在「170 MB 过桥 + `ui.decodeImageFromPixels`」，**解码只占 17%**。
所以这一页的问题不是「dav1d 慢」，是**位图尺寸**：
把位图从 170.8 MB 降到 3.4 MB，后面每一段拷贝跟着降两个数量级。

两条要记住的：

1. **`target_width` 不是画质旋钮，是这条路径可用性的前提。**
   `local_page_pixels` 现在收 `target_width: Option<u32>`；`None` 是原尺寸（**不放大**），
   传了才降采样。不给它，Rust 路就是「解 267 ms、搬 1260 ms」。
2. **降采样本身很便宜，dav1d 那一段缩不掉。** 缩到 768 px 只多花 55.6 ms
   （`imageops::thumbnail` 的 box 平均，比 `FilterType::Triangle` 快 2–3×，
   而 3× 以上的降采样倍数下两者肉眼无差）。
   但 **AVIF 没有可直接使用的 DCT 缩放档**（与 JPEG 的 1/8–1/1 不同），
   要缩放就必须先解全尺寸 —— 那 249 ms 是固定成本，只能靠预取把它藏到翻页关键路径之外。

另外，那次量到的「**上屏 3887.9 ms 不是真的上屏耗时**」，是个量具 bug：
Rust 路把新 `ui.Image` 赋给 `_rustImage` 之后**没有 `setState`**，而 `RawImage`
不像 `Image` 那样订阅 `ImageStream` —— 新图要等下一次**别的**原因触发的重建才被画出来
（用户不动鼠标就一直等）。那 3.9 s 就是这个「等」。同一次会话的正常值是 **14.5–29.8 ms**。
修法是在赋值处 `setState`，`postFrame` 回调才真的对应「画了这张图的那一帧」。
**`RawImage` 不订阅 ImageStream 这一条值得单独记**：它让「忘了 setState」从
「慢一帧」变成「无限期不出图」，而且会把等待时间记到别的段上。

### 5.4 降采样在「热重载构建」下被 opt-level 拖慢 3×（2026-09-16）

`rust/Cargo.toml` 的 `[profile.dev] opt-level = 1`（为了增量构建速度）。
降采样那一段原本写成 `image::imageops::thumbnail(&image, w, h)` ——
**泛型函数，实例化发生在 `rossi_local_core` 里**，于是它吃的是那个 1。

改成 `DynamicImage::thumbnail_exact(w, h)`（按具体像素类型在 `image` crate 内部展开），
再配一行

```toml
[profile.dev.package.image]
opt-level = 3
```

就只给这一个 crate 提优化。实测（同一页）：

| 档位 | `[profile.dev]` opt-level=1 | + `image` opt-level=3 | release 参考 |
|---|---|---|---|
| `thumbnail` → 768 | 226.7 ms | **67.7 ms** | 55.6 ms |
| `thumbnail` → 1440 | 229.7 ms | **93.0 ms** | 76.6 ms |

不直接抬 `[profile.dev].opt-level`：那会拖慢整个增量构建，而这个项目的日常就是热重载。
release 构建本来就是 opt-level 3，不受影响（所以这是 **debug 专属的浪费**，
只在热重载构建里付这个账）。

**可复用的经验**：Rust 里问「哪一段慢」时，要问的是「这段代码在**哪个 crate** 里被
实例化」，而不是「哪个 crate 定义了它」。泛型跨 crate 时这两者不同，
而 `cargo` 的 `[profile.*.package.*]` 是按**定义方**配的 —— 所以泛型要么挪到
定义方去调，要么就用定义方提供的非泛型入口。

## 6. 文件夹来源的两步策略

1. **平铺**：只列直接子文件。这是「一个文件夹就是一本书」的常见形态，也最便宜。
2. 平铺结果为空时才**递归**：因为「书籍目录 / 章节目录 / 页」同样常见，
   而它和第 1 步的判定信号互斥（有直接子文件就说明不是章节结构）。

不跟随符号链接（用 `file_type()` 而非 `metadata()`），所以既避免目录环，
也避免「一本书的页散落在链接外的磁盘上」这种让验收口径失控的情况。
递归深度上限 8 层、总文件数上限 20000，**超限直接报错而不是截断**——
截断看起来像成功了，比报错更糟。

## 7. 怎么验证

```bash
cd rust

# 单元测试（夹具就地生成，不依赖仓库里的二进制样本）
cargo test -p rossi_local_core

# 归档直读探针：不开 Flutter、不开 GPU
cargo run -p rossi_local_core --bin local_probe -- <路径> [--repeat N]
```

**解码能力**（哪一侧解得动）另有一条外壳侧的探针 —— 样本放在
`.workbuddy/tmp/*.avif` / `*.jpg` 时才会跑，不在就静默跳过：

```bash
# 真机引擎（App 实际用的那个）—— 判断「能不能显示」只看这一条
flutter test integration_test/avif_decode_probe_test.dart -d windows

# 测试宿主 flutter_tester —— 只记录宿主差异，**不能**当作 App 的能力
flutter test test/avif_decode_probe_test.dart
```

## 9. 接进 App（FRB 会话层，已实现于 `rust/src/api/local.rs`）

`LocalSource` 只保存路径与页元数据，所以「Reader session」由 Rossi 侧持有
（`START_WORK.md` §3.2）是自然的：在 windcore 里放一张 `id → LocalSource` 的表，
FRB 暴露下面这组函数，`local_close` 时释放。

```text
open_local_source(path) -> LocalSourceOpenResult { source | rejection }
local_source_pages(id)  -> Vec<LocalPageInfo>      // index / name / size
local_page_bytes(id, i) -> Vec<u8>                 // 该页的**编码字节**
local_close(id)         -> bool
local_open_session_count() -> u32                  // 判据 D 的探针
local_close_all()       -> u32
```

两处实现上的取舍：

1. **`open` 不用 `anyhow::Result`，改用 `LocalSourceOpenResult`。**
   本节开头那条「报错用类型不用字符串」在跨 FRB 时会被打回原形 —— `anyhow::Error`
   过桥后只剩 Dart 侧 `AnyhowException.message` 一个字符串。所以 open 的返回值里
   带一个 `LocalRejectionKind` 枚举（`UnknownFormat` / `RarSolid` / `RarNestedArchive` /
   `RarEncrypted` / `NotFound` / `Io`），类别信息以枚举过桥。
   其余接口（读字节等）的失败确实是意料之外的 IO / 损坏，继续用 `anyhow` 不会丢信息。

   注意 `LocalSource::open` 内部用 `with_context` 包了一层，所以分类要靠
   `downcast_ref` **向下穿透**，只看最外层消息会全部退化成 `Io`。

2. **`local_page_bytes` 传的是编码字节，不是像素。** 这与 ROADMAP「明确不做」里
   「不把所有图片转成 Dart `Uint8List` 再交给 Flutter」不冲突：那条禁止的是把
   **解码后的 RGBA** 搬过桥。上屏的目标形态是 Rust 侧解码后直接进 GPU texture
   （Phase 1 的 `texture-bridge`）；编码字节过桥只用于 Dart 侧兜底显示与尺寸探测。

会话表只存路径与页元数据，**体积与「打开了几本」成正比、与「读了多少页」无关** ——
这是判据 D 在 App 层仍然成立的原因，`local_open_session_count()` 就是它的量具。

判据 B/C/D 的测量都要求 Release 构建 + 真实内容，所以接线之后的第一件事是
`docs/windows-build/BASELINE.md` 那套口径下的真实漫画实测。

### 11.1 调试页 `lib/debug/local_source_debug_page.dart`

入口：设置 → 调试 → **本地来源读取（判据 A）**。刻意走 `MaterialPageRoute`
直连而不是 `@RoutePage()`：调试页不值得为它补 `slang` 词条 + 触发一次全量
auto_route codegen。要转正时再补。

它能做什么：

- 打开**散图文件夹**（`getDirectoryPath`）或 **CBZ / CBR**（`openFile`）。
- 左侧页列表（序号 / 名称 / 编码字节数），右侧 `InteractiveViewer` + `Image`。
- 顶栏常驻 `local_open_session_count()` 探针；换书自动 `local_close` 旧会话，
  退出页面在 `dispose` 里关会话 —— 忘了关会立刻在探针上显形。
- **翻页分段计时**（见 §12）：把一次翻页拆成「读页 › 解码 › 上屏」三段分别显示，
  并给出解出的像素量、RGBA 位图大小、当前页格式与 Flutter 全局图片缓存的占用。
  保留最近 6 次记录，用于对比解码模式切换前后的差异。
- **解码模式开关**：`显示尺寸`（默认）按预览区宽度 × 设备像素比解码，`全尺寸`
  则解归档里的原始尺寸。这不是优化项而是**量具** —— 两个模式的差值就是
  「解码 + 上屏成本随像素量增长」的直接证据。
- **逐页读一遍并计时**，输出合计 / p50 / p95 / max，以及
  「前 5 页均值 → 后 5 页均值」的比值，直接给出 §7 那条判定：
  比值 < 2 视为近似常量（按需 seek），否则疑似整段解压。
- **预取开关**：`预取：开`（默认）时，翻完一页后会把 **±1 页**解好并建好 `ui.Image`，
  翻到时路径上只剩「换引用 + 画一帧」（实测 20–30 ms）。这是「翻页 < 200 ms」
  唯一成立的理由，理由与实测见 §12.4。关掉它即可看到「每次翻页现解」的原始数字。
- 被拒绝时按 `LocalRejectionKind` 显示类别、原文与下一步建议。

四条必须一起读的限制：

1. **它是 Dart 兜底显示路径。** Flutter 负责解码，即「编码字节过桥」—— §9 允许，
   但它**不是**目标形态。**不要拿它的帧率当判据 B/C**：判据 B/C 要等 GPU 上屏接线
   （Rust 侧解码 → texture）。
2. **不缓存归档句柄，只缓存「解好的 ±1 页」。** 每次翻页都重新 `local_page_bytes` ——
   让「不常驻句柄」在 UI 上可见。缓存只有预取那一份，且有界（≤3 页 / ≤64 MB；
   全尺寸档位下不预取），缓的是**派生结果**而非归档内容，判据 D 的结论不变。
   **解码结果换页即释放**：真实扫描页单页 RGBA 位图可达 179 MB，远超 Flutter
   默认 100 MB 上限，不释放会变成反复解码 + 内存震荡（实测进程 RSS 一度到 592 MB）。
3. **默认按显示尺寸解码**，放大超过约 2× 会看到模糊，属预期。要量全尺寸成本，
   把开关切到 `全尺寸`。
4. 计时口径见 §12：读页含 FRB 过桥，解码是纯解码，上屏含纹理上传与首帧绘制，
   合计误差约 ±1 帧。绝对值仍以 `local_probe`（Rust 侧）为准。
   标着「预取命中」的那一行解码/建图为 0 —— **成本发生在你读上一页的时候**，
   同一行会把它报出来，别把它读成「解码变快了」。
5. **预取只接在 Rust 路径上**（外壳路径的位图在全局图片缓存里，要接得用
   `precacheImage`，未做）—— 所以 jpg 归档目前享受不到。

## 12. 翻页延迟归因（真实漫画实测）

起因：调试页上「上次读页 60 ms」看着不高，但**点击翻页到出图慢了半秒**。
结论：那个数字只量了读取，**主体成本在解码**。

> **这一节量的是外壳路径（编码字节交给引擎）。** Rust 路径的归因结论完全不同 ——
> 瓶颈是位图搬运而不是解码，见 **§5.3**。两条路径别混着引用。

样本：`E:\1Hub\EH\G44不会受伤 八奈见杏菜（泳装）.cbz`
（29 页 / 99.2 MB；单页 JPEG **44.8 MPix**；29 条 DEFLATE + 1 条目录，非固实）。

> 这是**偏极端**的样本：相机原片级分辨率（8192×5464 或转置，单页 3–6 MB），
> 比典型漫画扫描页（1–2 MPix）重一两个数量级。下面的数是**最坏情况**，
> 不能外推成「每本漫画都会慢半秒」；但判据 C 必须扛得住最坏情况，所以结论不变。

| 阶段 | 实测 | 占比 |
|---|---|---|
| 读页（inflate + CRC + FRB 过桥） | Rust 探针 **3.8–29 ms**；App 内 **60.9 ms** | ~10% |
| 解码（全尺寸 44.8 MPix） | Rust `image` **193–270 ms**；Skia **332 ms** | **~65%** |
| 上屏（位图上传 + 首帧绘制） | 余下 **约 100–200 ms** | ~25% |

> **「上屏」这一行的口径后来被推翻了一半**，别当硬结论引用。它由
> 「解码完成 → `postFrame` 回调执行」相减得到，而 `postFrame` 回调只在
> **有新帧被调度**时才跑。外壳路径靠 `Image` 自己订阅 `ImageStream` 触发重建，
> 通常是准的；但只要有一次「没有新帧」，这一段就会把用户的等待时间记进去 ——
> Rust 路径上实测到过 3887.9 ms 的假值（真值是 14.5–29.8 ms，原因见 §5.3）。
> 要量上屏，应当用 `SchedulerBinding.addTimingsCallback` 拿 `FrameTiming.rasterDuration`，
> 而不是拿帧的边界相减。

三个**已排除**的怀疑对象（都量过）：

- **不是磁盘**：同一文件顺序读 **2646–3798 MB/s**（NVMe），读完整包 99 MB 只要 26–37 ms。
- **不是归档寻址**：逐页读一遍近似常量，非固实按需 seek（§7 的判定）。
- **不是页序 / 缓存策略**：换页即关归档，不常驻句柄。

### 12.1 解码到「显示尺寸」的收益

`test/decode_cost_probe_test.dart` 在 `flutter_tester` 里单独量解码（不含纹理上传与
UI 调度），同一张图：

| 目标宽度 | 解码 | 像素量 | RGBA 位图 |
|---|---|---|---|
| 全尺寸 | **332 ms** | 44.8 MPix | **179.0 MB** |
| 1600 px | 140 ms | 3.8 MPix | 15.3 MB |
| 800 px | **72 ms** | 1.0 MPix | **3.8 MB** |

即解码 **4.6×**、位图 **47×**。注意**不成正比**：像素量降 45× 只换来 4.6× —— 说明
Skia 在比例缩小时仍要「先解后缩」，没有一路走 JPEG 的 DCT 缩放解码。
**这正是不能把希望寄托在 `cacheWidth` 上的理由。**

### 12.2 对本层的三条直接结论

1. **判据 C（p95 ≤ 16.7 ms）不可能由「CPU 全尺寸解码」达成。** 连**解码到 800 px 的
   72 ms** 都放不下，更不用说全尺寸的 332 ms。目标形态只能是 Rust 侧按需 / 分块解码
   后直接进 GPU texture，并且**解码必须落在翻页关键路径之外**（预取或提前一页）。
   这条与 Phase 1 `texture-bridge`、Phase 2 tile 化是同一件事。
2. **读页的 60 ms 里约 40 ms 是过桥开销。** 同一条目 Rust 探针 4–29 ms、App 内 60.9 ms；
   磁盘已排除，差额只能落在 FRB 的 `Vec<u8>` → `Uint8List` 拷贝、`spawn_blocking`
   调度与 Dart 侧分配上。又一次说明**编码字节不该过桥** —— 这条桥本身就有量级问题。
3. **inflate 有明确优化余地（候选，未做）。** 3.3 MB 条目 Rust 侧读 12–29 ms
   （≈120–230 MB/s），而 deflate 对已压缩 JPEG 几乎没压缩（`comp ≈ raw`），说明时间
   花在 inflate 的哈希链搜索与 CRC 上而非磁盘。`flate2` 默认后端是 `miniz_oxide`
   （纯 Rust），换 `zlib-rs` / `zlib-ng` 通常有 2–4× 收益。**先不动**：等 Phase 1
   接线后重测，届时它才在 16.7 ms 预算里占实际份额。
4. **Rust 路径的结论与上表相反：瓶颈不是解码，是搬运。** 见 §5.3 ——
   Rust 侧解同一张 44.8 MPix 只要 267 ms（dav1d 249 ms），而把 170.8 MB 位图
   过桥 + 交给 `decodeImageFromPixels` 要 1260 ms。
   所以那条路上的**降采样比换更快的解码器有效得多**，因为它砍的是搬运而不是解码。
   两条路径合起来其实是同一句话：**44.8 MPix 解出来之后的任何一个后续动作都不该在
   CPU 上发生** —— 要么别解这么大（降采样 / tile），要么别搬（GPU 侧直接消费）。

### 12.3 复现方式

```bash
# 1. 拆解一个归档：条目、压缩方式分布、冷读 vs 纯磁盘读、图像格式与像素量
python poc/local-samples/inspect_cbz.py "<你的.cbz>"

# 2. 单独量解码成本（样本不在时自动跳过）
flutter test test/decode_cost_probe_test.dart

# 3. 量 Rust 侧读页 / 解码真值
cd rust && cargo run -p rossi_local_core --bin local_probe -- "<你的.cbz>"

# 4. 把「解码 / 装箱 / 降采样」拆成单价（决定 Rust 路径该不该降采样）
cd rust && cargo run --release -p rossi_local_core --bin scale_probe -- "<你的.cbz>" 0

# 5. 量 dav1d 到底用上了几个核（见 §12.4）—— 改进程亲和性掩码再跑第 4 条
#    mask=0x1 只给 1 个逻辑核，mask=0xffff 给全部 16 个
python -c "
import ctypes,subprocess
from ctypes import c_void_p,c_size_t
k=ctypes.windll.kernel32
k.GetCurrentProcess.restype=c_void_p
k.SetProcessAffinityMask.argtypes=[c_void_p,c_size_t]
k.SetProcessAffinityMask(k.GetCurrentProcess(),0x1)   # ← 换成 0xffff 对照
subprocess.run([r'rust\target\release\scale_probe.exe','<你的.cbz>','4'])
"

# 6. 看硬件 AV1 解码器收不收这个文件（见 §12.4）
ffmpeg -hide_banner -decoders | grep -i av1      # 有没有 av1_cuvid / av1_qsv / av1_amf
ffmpeg -y -c:v av1_cuvid -i page.avif -f null -
```

`poc/local-samples/inspect_cbz.py` 是只读诊断脚本，把「冷读」与「纯磁盘顺序读」分开
计时，用来把「读页慢」在**磁盘 / inflate / 过桥**三者之间归因，而不是靠猜。

### 12.4 解码地板：软硬两侧都试过了（2026-09-16）

起因是一句直白的要求：「必须优化到 200 ms 以下，你有用上 GPU 纹理吗」。
先回答后半句：**没有。** 当前上屏是 `decodeImageFromPixels`（Rust 解好的 RGBA 过桥 →
`ImmutableBuffer` → `ui.Image`），GPU texture 直通是 Phase 1 的 `texture-bridge`。
但**它救不了这个数字**：降采样后位图只剩 4.4 MB，过桥与建图两段合计 20–30 ms，
而解码那一段是 340 ms。把那 30 ms 全砍掉也到不了 200。

于是只剩解码可动，三条路都量了。

**① 软件解码没有余量。** 用进程亲和性掩码限制可用核数，跑同一个 `scale_probe`：

| 可用逻辑核 | dav1d 解码（同一页，5464×8192） |
|---|---|
| 1 | 610–667 ms |
| 2 | 554–580 ms |
| 16 | **269–295 ms** |

默认设置（`dav1d_default_settings` → `n_threads = 0` = auto）**已经在用全部 16 核**，
1 → 16 核只换来 **2.25×**。这条流几乎没有 tile 级并行空间（`ffmpeg -threads 1..16`
的曲线形态一致），而 dav1d 已是当前最快的软件 AV1 解码器。
**地板 ≈ 270 ms，这是硬成本。**

**② 硬件解码被色彩格式挡住。** `av1_cuvid`（NVDEC）对同一样本直接拒绝：

```
[av1_cuvid] Codec av1_cuvid is not supported with this chroma format.
```

这本漫画的 AVIF 是 **4:4:4**（`ffmpeg -i` 报 `yuv444p(pc, bt709)`），
而 AV1 硬件解码器（NVIDIA / Intel / AMD 一致）只吃 4:2:0。
`av1_qsv` 报无可用 MFX 实现（本机无 Intel GPU），`av1_amf` 访问违例 ——
**三条硬件路径全灭**，不是没试。

> 顺带记一个坑：用 ffmpeg 量解码速度时别走 `-f rawvideo -`（管道写 134 MB）或
> 默认 `-f null`（会插一次 444→420 的 swscale）。这两种口径都能把结论污染到
> 3× 以上。要量 dav1d 的绝对速度就用 §12.3 第 4 条那个探针。

**③ 所以「< 200 ms」只能在翻页路径之外达成 —— 预取。**
翻完一页后把 ±1 页解好（连 `ui.Image` 一起建好），翻到时路径上只剩
「换个引用 + 画一帧」，实测 **20–30 ms**。

这次的结论要说全，别让人误读：

- **成本没有消失，是被挪到用户读上一页的时候了。** 所以调试页在「预取命中」那一行
  同时报出「预取时花了多少（解码 + 建图）」，关掉「预取：开」再翻同一页就能看到
  它的真实总价。没有这个对照，那个数字会读成「解码变快了」。
- **「冷页 < 200 ms」在当前形态下不可能达成**（270 ms 是地板）。
  能达成的是「翻页 < 200 ms」，前提是那一页被预取过。
  连冷页都要进 200 ms，只有两条路：Phase 2 的 tile 化（解 tile 而不是整页），
  或者换掉 4:4:4 的源（4:2:0 的 AV1 一般快 2× 以上，且能吃硬件解码）。
- **预取只接在 Rust 路径上。** 外壳路径的位图在 Flutter 全局图片缓存里，
  那是另一套机制（要接得用 `precacheImage`），未做 —— 而 jpg 归档走的正是外壳路径。
- 预取是**有界**的（≤3 页 / ≤64 MB，缓的是派生结果不是归档内容或句柄），
  判据 D 的结论不变；全尺寸档位下不预取（一页 179 MB）。

### 12.5 预取与并发控制：把 mImageViewer 的两个策略模块搬进 `local_core`

§12.4 的预取一开始是**手搓**的（翻页后延迟 180 ms + 一个 `_prefetchBusy` 布尔）。
它证明了这个方向值钱（翻页 426–531 ms → 27 ms），但那份实现是玩具：
「等多久」和「同时跑几个」都靠拍。

mImageViewer 里本来就有一对**纯策略模块**在解同一件事，现在按它的形状搬进了 `local_core`：

| 本地 | 上游 | 提供什么 |
|---|---|---|
| `prefetch_policy.rs` | `src/app/prefetch_policy.rs` | `decide_prefetch_allowed`（准入判决 + 理由）、`interleaved_prefetch_positions`（目标顺序 `+1,-1,+2,…`） |
| `page_load_scheduler.rs` | `src/fs_page_load_scheduler.rs` | 进程级**许可模型**：总 6 张，2 张留给高优先级；`Sequential` / `LatestSeek` 两种契约 |

搬运形态、偏离清单与**同步步骤**单独成文：`docs/local-core-vendored-modules.md`
（配套 `script/sync_vendored_modules.py` —— 上游更新时用它判断「这份要不要跟着改」）。

> **为什么只能搬源码**：上游这两个模块分别藏在私有 `mod app;` 与私有
> `mod fs_page_load_scheduler;` 之下、内里一律 `pub(crate)`，path 依赖拿不到。
> 搬的时候保住了上游的**函数名 / 类型名 / 常量名 / 测试名**，就是为了以后能同步。

**语义映射**（上游是连续阅读，我们是分页阅读，判据同构）：

| 上游 | 这里 |
|---|---|
| `last_prefetch_scroll_at` | 上一次翻页/跳页的时刻 |
| `visible_state_pending` | 当前页是否还在加载 |
| 滚动 idle 阈值 100 ms | 翻页后静默 100 ms 才允许预取 |
| 3 s backstop | 同上（防止「当前页永远加载不出来」把预取永久冻死） |

判决与目标选择**都在 Rust 侧**；Dart 只递状态、显示结果。
`decide_prefetch_allowed` 每 50 ms 问一次（上游是每帧问一次 —— 宿主从 egui 的帧循环
换成 Flutter 的定时轮询，门槛本身没变）。**刻意不在 Dart 侧写第二套策略**：
一旦本地也判一次，`prefetch_policy` 那 13 条测试就管不到真实行为了。

**许可模型解决的是什么**：不加限制时「预取 2 页 + 用户翻页」会同时解 3 张全尺寸 AVIF
（每张 179 MB 位图）。现在：

- 翻页请求是 `High`，预取是 `Normal` —— 调度器留 2 张许可**不给** `Normal`，
  所以「预取把许可占满、用户那一页排在后面」在**结构上**不可能发生，不是靠调参；
- `LatestSeek`（跳页 / 重读当前页）会作废同一会话里**还在排队**的旧请求 ——
  用户已经改主意了，中间那些页读完也没人看；
- `Sequential`（相邻翻页）**永不**作废 —— 连翻三页就是三页都要，中间那页用户真的看过。

**新增的失败类别**：`LocalDecodeFailureKind::Cancelled`。被更新的跳页取代**不是错误** ——
这一页完全可能解得出，只是没人要了。与 `DecodeFailed` 混在一起会把用户误导成「这本解不了」。

**还没接**：`should_prefetch_final_effect`（连续阅读的 keep-set / LOW 水位门）已经搬进来、
带测试，但没桥接 —— 分页模式下它恒 `Allow`。等 Phase 2 的双页/滚动模式再启用。

**验证**（2026-09-16 实测）：

```bash
cd rust
cargo test -p rossi_local_core          # → 54 passed（31 原有 + 23 新搬/新写）
cargo test -p windcore --lib api::local # → 12 passed
```

### 12.6 预取与翻页并发解码 = 双输（2026-09-16，真机实测 + 照上游修）

§12.5 的让路机制有个洞：**它只保证翻页拿得到许可，不保证翻页不跟预取分核。**
2026-09-16 真机复现（同一本 AVIF，`尺寸：显示`）：

| 观测 | 数值 | 说明 |
|---|---|---|
| 预取**单独**跑一页 | **431.6 ms** | 与 §5.3 的单价表对得上（dav1d 249 + 降采样 + 装箱 + 过桥 + 建图） |
| 翻页时「解」这一段 | **572.1 / 647.7 / 550.6 ms** | 比单独跑慢 **33–50%** |
| 预取**命中**的翻页「屏」 | 两次会话对比：**29.4 / 32.4 / 58.9 / 85.9 ms**（位图 14.3 MB）<br>**87.9 / 143.6 / 257.6 / 145.1 / 99.3 ms**（位图 1.5 MB） | **位图小了 10 倍，反而更慢** —— 所以这不是纹理上传的问题 |
| 那一刻的许可 | `1/6 张在用（1 张是预取），1 个在等` | 预取持着许可在跑，同时用户在等翻页 |

**三条数据指向同一个原因：dav1d 一条流几乎不能并行，所以「并发两个解码」不是分核，是两边都慢一倍。**

这不是猜的：§12.4 量过 dav1d 的线程伸缩 —— **1 核 610–667 ms / 2 核 554–580 / 16 核 269–295 ms，1→16 只有 2.25×**。
一条流已经把核吃满（后经本节分核实测细化：**实际天花板 ≈ 8 核**，见下），再并发一个就是让两者各拿一半。**顺带把 Flutter 的帧生产也饿住了** ——
那才是「预取命中了，翻页还是要等 87–258 ms 才出帧」的来源（CPU 全在解码，UI/raster 线程排在后面）。

**修法照上游，不自己发明。** mImageViewer `update_prefetch_window`（`src/app.rs:55192`）的做法是：
**当前页还没有可显示内容的时候，取消其它 pending，并且连新的预取也不发。**
上游把这段撤过一次（判断「有 High 预留位就不需要」），实机立刻变差：

> 取消中占的额度是 5/6 → 6/6、`running` 的中位数是 0、页面完成是 **p50 148 ms → 396 ms**。
> 原因是，**已经拿到 permit 的预取会 commit 到一段不可中断的读取上，约 700 ms**。

对应到我们的调试页（三处，都在 `lib/debug/local_source_debug_page.dart`）：

1. **翻页发起时立刻 `_prefetchGeneration++`** —— 在跑的那一轮跑完当前页就退场，不再发起下一页。
   对应上游的「取消其它 pending」。
2. **每解完一页重新问一次「用户在等吗」**（`running - runningNormal > 0 || waiting > 0`）→ 整轮退出。
   光靠第 1 条不够：用户完全可能在循环已经在 `await` 里的时候翻页。
   对应上游的「也暂缓发起新的预取」。
3. **窗口 `±1` → `forward 2 / back 1`**。

**第 3 条是刻意偏离上游的，理由必须写下来 —— 而且理由不是「上游的页便宜」。**

上游全屏页预取的默认窗口是 **`prefetch_forward = 12` / `prefetch_back = 4`**
（`settings.rs:6065`，keep 各 +1）。它敢开这么大，是因为它的解码**一张只占一个核**：

| 上游事实 | 位置 | 结果 |
|---|---|---|
| 全屏（canonical）解码主路径是 **`image` crate**：`image::load_from_memory` / `image::open` | `canonical_image_loader.rs:453/466` | JPEG 走 zune-jpeg、PNG 走 png —— **都是单线程，一张一个核** |
| **WIC 只是 fallback**（第二顺位），顺序被测试钉住：`image` → WIC → Susie | `canonical_image_loader.rs:455/468`、测试 `byte_fallback_order_is_image_then_wic_then_susie`（:1420） | WIC 在常规页上**根本不跑** |
| `wic_decoder.rs` 354 行：一次 `CopyPixels`、**无 `IWICBitmapSourceTransform`**、无 rayon | `src/wic_decoder.rs` | 就算走到它，也是**全尺寸、单线程、不做解码侧缩放** |

**所以上游的「6 张许可并发」是真并行（6 个核），窗口开大 = 纯赚吞吐。**
上游单张解码其实也不快 —— **它快在「用并发把单张的慢藏起来」，不是单张更快。**

> **这里有个比「我们实现得不对」更要紧的事实**：上游这套并发模型**建立在
> 「一张图一个核」这个前提上**，而 `image` 的 **avif** 后端是 dav1d ——
> **一条流吃满 16 核**。也就是说，**AVIF 会把上游那套模型同样打破**；
> 我们整本都是 AVIF，所以**我们从一开始就没有那条路可走**。这不是我们的实现缺陷。

**我们这边的确切前提**：`image` 的 avif 后端是 `dav1d::Decoder::new()`
（`image-0.25.10/src/codecs/avif/decoder.rs:82`，默认 `n_threads = 0` = auto），
一条流吃满 16 核（§12.4：1→16 核只有 2.25×）。
并发不是分核，是两边都慢一倍 —— **照抄上游的并发度在这里只会更差**。

所以窗口按「用户读一页能备好几页」定（`forward 2 / back 1`），不照抄 12/4：
那会变成一轮预取跑 8.7 秒、全程占着核。而且串行之下**窗口不是瓶颈、吞吐才是** ——
用户读一页 2 秒，最多也就备好 3–4 页。

> **要把上游那条「并发换吞吐」的路在我们这边重新打开，唯一的钥匙是
> 「按优先级分配 dav1d 的线程数」**：翻页那一张给全核（249 ms），
> 预取那几张各给 2–4 个核（单张变慢，但**完全不打扰翻页**）。
> 这是把「并发」在单流不可并行的解码器上重新变成纯收益的唯一形态。
> **卡点**：`image` 不暴露 `dav1d::Settings`（`Decoder::new()` 直接吃默认值），
> 要做得绕开它的 avif 封装（容器解析 + YUV→RGB 共 672 行）或给它打补丁 ——
> **独立工作项，不在本轮。**

**上面说的「先量一件事」当天就量完了**（`poc/dav1d-threads/thread_probe.py`：
进程亲和性掩码约束可用核 + `GetProcessAffinityMask` 回读复核（§12.4 的坑），
同一页 5464×8192 = 44.8 MPix，`rounds=1` 单次解码）：

| 可用核 | 1 | 2 | 4 | 8 | 16 |
|---|---|---|---|---|---|
| 单张解码 ms | 696.2 | 530.1 | 349.1 | 269.3 | **251.8** |

并发对照（两路各钉 8 核、同时起跑，模拟「翻页 + 预取」公平分核）：**339.0 / 346.7 ms**。

三个结论：

1. **伸缩天花板在 8 核附近，不是 16**：1→8 = 2.59×，8→16 只再快 7%。
   把 §12.4「一条流吃满 16 核」说得更准：**吃满的是 ~8 核，后 8 个核基本在陪跑**（内存带宽到顶）。
2. **并发的代价分两层**：公平分核（8+8）时翻页要 340 ms，比串行的 252 ms 慢 35%；
   而 App 里观测到的 550–648 ms 已经贴近**单核**的 696 ms ——
   **App 里的翻页实际是被预取那路 auto=16 线程饿到只剩 ~1 个核**，不是「各拿一半」。
   让路修法（串行）拿回的就是这 300–400 ms。
3. **「按优先级分核」的收益有了刻度**：翻页给全核（≈252 ms，超过 8 核不涨），
   预取每张给 2–4 核 = 530 / 349 ms —— 单张慢、但**完全不打扰翻页**，
   `forward 2 / back 1` 在 2 秒的阅读停留里备得完（530 ms × 3 页 ≈ 1.6 s）。
   **收益明确，但仍然被 `image` 不暴露 `dav1d::Settings` 卡着**，维持「独立工作项」定性不变。

**顺带一个反直觉的核实结果**：`image` 的 avif 解码在**有 alpha 时才**建第二个
`dav1d::Decoder`（`decoder.rs:88`）—— 我们的照片页没有 alpha，所以只有一个解码器在跑。
但**带 alpha 的 AVIF 页会同时跑两个 dav1d 实例**，单页成本接近翻倍。
漫画页一般没有 alpha，真遇到时别忘了这条。

**顺带补的两件量具**（都记着「先量再宣称」的纪律）：

- **`FrameTiming` 分解**：页面上现在显示 `build / raster / vsync`。
  这条纪律项目里早写过（§12.2）但一直只是纪律 —— 「上屏」用 postFrame 相减量出来的数
  里混着「等下一帧 vsync」，143 ms 到底是**等**出来的还是**画**出来的，只有 `rasterDuration` 能回答。
- **每行标注「解码时与预取并发 N 张」**：许可数在翻页结束时就变了，事后看 `解码许可` 那一行
  是看不到病根的。把「这一次解码有没有被预取抢核」记在那一页自己身上。

**残余成本（照实说）**：已经**开始**解码的那一页取消不掉 —— `acquire_cancellable` 只覆盖
「等许可」阶段，dav1d 一次调用不可中断（上游同一处妥协，见上面引文里的「不可中断的读取」）。
所以最坏情况下翻页仍会与一页预取重叠，重叠时长 ≤ 单页解码时间。要消掉它只能靠
**把单页成本本身压下去**（GPU 上屏 / Phase 2 的 tile 化），不是再调策略。

**下一步的杠杆已经换人了**：往上是「预取」，现在是**「Rust 解码 → GPU 上屏」**
（Phase 1 的 `texture-bridge`）。降采样那一段（~100–130 ms）的成本 ∝ **源面积**，
上游干脆不做 CPU 降采样（全尺寸给 GPU Lanczos）—— 我们照抄不了，因为 AVIF
没有 JPEG 那种 DCT 缩放档，必须先把全尺寸解出来（§5.3）。所以这一段的解法是
**别再把位图搬过 CPU**，不是换个更快的重采样。



### 12.7 三格式基线：JPEG / AVIF / JXL（2026-09-16，内容侧路线的单价表）

同一本漫画（29 页，G44 八奈见杏菜・泳装）的三种载体，`D:/1Dev/tmp`：
原版 JPEG **99 MB** / AVIF 重编码 **19.5 MB** / JXL 重编码 **18.6 MB**。

量具：`scale_probe --features jxl-probe[,jxl-probe-libjxl]`。JXL 有两个后端
（`--jxl-backend oxide|libjxl`）：**jxl-oxide 0.12**（纯 Rust，rayon 全核池）与
**jpegxl-rs 0.15 = libjxl 0.12 官方 C 库**（`vendored` 静态编译，`ThreadsRunner` 全核池）；
JPEG 走 zune-jpeg；AVIF 走 dav1d。全部经 `image::DynamicImage`，下游缩放/装箱同一条路。
`--rounds 2/3` 取最小值，全尺寸解码段：

| 页 | MPix | JPEG | AVIF | JXL (jxl-oxide) | JXL (libjxl) |
|---|---|---|---|---|---|
| idx 0 | 14.0 | 33.0 ms | 51.0 ms | 290.6 ms | **44.0 ms** |
| idx 9 | 44.8 | 113.0 ms | 150.2 ms | 937.0 ms | **121.9 ms** |
| idx 19 | 9.9 | 27.1 ms | 44.0 ms | 205.2 ms | **36.8 ms** |

结论：

1. **jxl-oxide 的 8× 慢是纯 Rust 实现的问题，不是格式的** —— 同一份 JXL 文件，
   libjxl 比 jxl-oxide 快 **6.6–7.7×**。用「现成纯 Rust 栈」评估 JXL 会得出完全错误的结论
   （初版结论「内容侧换 JXL 不划算」就是这么错的，已在 libjxl 实测后修正）。
2. **修正后的判决：内容侧换 JXL 是三条里最优的**：
   - 解码：44.8 MPix **121.9 ms**，比 AVIF（dav1d，150.2 ms）快 **19%**，与 JPEG（113 ms）基本持平；
   - 体积 **18.6 MB** vs AVIF 19.5 MB vs JPEG 99 MB；
   - 且 JXL 还有没兑现的余量：DCT 渐进缩档（libjxl C API 有 progressive/低分辨率渲染，
     jpegxl-rs 封装没暴露）——「解码到显示尺寸」在 AVIF 上无解（§5.3），在 JXL 上理论可解。
   - 代价：jpegxl-rs 封装是 **GPL-3.0-or-later**（libjxl 本体 BSD-3）。toy 项目按用户拍板可无视；
     若哪天要正经分发，得自写 BSD 侧薄 FFI（libjxl 解码面很小）或进程隔离。
3. **`local_core` 对 JXL 页报 `shell-only` 是对的**：真要吃 JXL 内容，得把解码器引进
   App 解码路径。两个后端的接入方式都已打通：`jxl-probe` / `jxl-probe-libjxl` feature 门
   （见 `scale_probe.rs`），各自 `DynamicImage` 无缝接入，零手写解码代码。
4. **libjxl vendored 编译的三个坑（本地补丁，见 `rust/Cargo.toml` `[patch.crates-io]` 注释）**：
   - jpegxl-src 硬编码 `.generator_toolset("ClangCL")` —— 本机 VS BuildTools 没装该组件
     （MSB8020），删掉回落默认 MSVC；
   - 它还硬编码 `CMAKE_MSVC_RUNTIME_LIBRARY=MultiThreaded`（/MT），与 Rust 工具链的 /MD
     冲突（LNK2038），改 `MultiThreadedDLL`；
   - **cmake-rs 会用自己的 MSVC 基础 flags（无 /O2）覆盖 CMake 默认 Release 优化 flags**
     —— libjxl 被 O0 编出来，实测比 jxl-oxide 还慢 8 倍（8025 vs 937 ms @44.8 MPix）。
     必须显式 `.cxxflag("/O2 /Ob2 /DNDEBUG")`。**「慢得反常」先查编译优化再下结论。**
   - 补丁副本在仓库外 `D:/1Dev/vendor/jpegxl-src-0.12.0`（本地路径，未随仓库分发）；
     复现方法：拷 registry 里的 jpegxl-src-0.12.0、改 `src/lib.rs` 三处即可。
5. **其余实现层的坑，都已在代码注释里**：
   - `image` 0.25.10 **没有 jxl feature**（feature 全表核实过）；「image 集成」在
     jxl-oxide 侧（`image` feature 提供 `JxlDecoder`）与 jpegxl-rs 侧（`ToDynamic` trait），
     两者依赖的都是 image 0.25，不会双份编译。
   - **dev-dependencies 进不了 bin 目标**（E0433 实测）——探针要用就得进
     `[dependencies]` + `optional = true` + feature 门，不能图省事放 dev-deps。
   - 探针既有 bug 顺手修掉：页宽 < 4096 时第一档被跳过，`rows[slot]` 越界 panic
     （idx=19 三本全崩，exit=101）。改成按 TARGETS 长度预铺 `Option`。
   - scoop 的 `libjxl` 包不可用于链接：`jxl.lib` 是 0 字节占位、包内无 `jxl.dll`
     （pkgconfig 自称 x64-windows-static 但连 `jxl-static.lib` 都没有）——别再试它。

### 12.8 jxl-rs 实测：带线程池反超 libjxl，且是 BSD-3 纯 Rust（2026-09-16）

用户指出 `jxl-rs`（libjxl 官方组织的纯 Rust 解码器，**Chrome 145 / Firefox 采用中**，
BSD-3-Clause）值得单独测 —— 它与 jxl-oxide 是完全不同的项目。crates.io 上核心叫
`jxl`（0.7.3）、image 集成叫 `jxl-image-rs-integration`（0.7.3，走 `image::hooks` 注册）。

**关键口径发现：官方 image 集成把 `parallel_runner` 硬编码成 `None`（单线程）。**
不补线程池，「jxl-rs vs libjxl」的差距分不清是实现的锅还是线程的锅。因此探针加了
`jxlrs-mt` 档：绕开集成，用 `jxl::api` 直接驱动 + rayon runner（`JxlParallelRunner`
trait 只要求 `run` + `num_threads`，rayon 实现约 15 行，见 `scale_probe.rs`）。
同口径还给 libjxl 加了 `libjxl1t` 档（不挂 parallel_runner）。

全尺寸解码 ms（同一本 29 页，`--rounds 3` 取最小）：

| 页 MPix | JPEG (zune, 1T) | AVIF (dav1d, ~8核) | jxl-oxide (rayon) | libjxl (全核) | libjxl (1T) | jxl-rs (1T, 官方集成) | **jxl-rs (rayon 全核)** |
|---|---|---|---|---|---|---|---|
| 14.0 | 33.0 | 51.0 | 290.6 | 44.0 | 269.4 | 184.0 | **34.8** |
| 44.8 | 113.0 | 150.2 | 937.0 | 121.9 | 882.5 | 562.9 | **91.2** |
| 9.9 | 27.1 | 44.0 | 205.2 | 36.8 | 199.6 | 136.4 | **30.2** |

结论（更新 §12.7 的判决）：

1. **单线程同口径，jxl-rs 反超 libjxl ~35%**（562.9 vs 882.5 @44.8 MPix）——
   「纯 Rust 重写比 C++ 慢」在这个实现上不成立，浏览器级优化的成色是真的。
2. **带线程池，jxl-rs 三页全部反超 libjxl ~25%**，比 dav1d 快 1.6–2.3×，
   几乎追平 JPEG 解码。**jxl-rs 是目前测过的所有解码路径里最快的。**
3. **jxl-rs 是 BSD-3-Clause**（crates.io 核实）——不像 jpegxl-rs 是 GPL 封装。
   纯 Rust、零 C 构建、无运行时 DLL 依赖。**作为 App 解码路径，jxl-rs 全面优于
   jpegxl-rs（GPL + C 构建）与 jxl-oxide（慢 10×）。**
4. 官方集成的单线程限制是个已知事实（`process(..., None)` 硬编码），接 App 必须
   自己带 runner —— 直接用 `jxl::api` + rayon runner（探针 `decode_jxl_jxlrs_threaded`
   就是现成参考实现，含 NeedsMoreInput 循环与 8-bit 分支）。
5. **DCT 缩档问题的分格式现状**（用户问「DCT 能不能实现」）：
   - **JPEG：能，上游已做** —— mImageViewer 用 TurboJPEG 的 `tj3SetScalingFactor`
     （M/8 档），`pick_dct_scale_num` 设计+测试齐全（`docs/dct-scale-plan.md`，
     实测 2.5× 提速、PSNR 51dB）。代价是引 turbojpeg 依赖。
   - **AVIF：无解**（§5.3 实测过，dav1d 解码 ms 不随目标尺寸降）。
   - **JXL：格式支持渐进（DC 帧即 1/8 分辨率），但 jxl-rs 0.7.3 的高级 API 未暴露
     progressive-detail 控制**（只有 `flush_pixels` 用于帧间预览）；libjxl C API 有
     `JxlDecoderSetProgressiveDetail` + `FlushImage`，真要「解码到显示尺寸」得走 C 侧。
   - **但先别急**：jxl-rs 全帧解码已经 30–91 ms，DCT 缩档在 JXL 路径上的边际收益
     远小于它在 JPEG 巨页上的意义 —— 除非将来把解码做到关键路径里（判据 C）。

### 12.9 JXL 进 App 解码路径：编译期 feature 三选一（2026-09-16，随 §12.8 结论接线）

§12.8 的结论落成代码：`jxl` 进 `decode()` / `probe_size()` 的正式路径，后端用
**编译期 feature** 选择（不设新分支，主线上可切换）。

- **`local_core` 侧**（`src/jxl_backend.rs`，feature 门控模块）：
  - `jxl-rs-mt` = `jxl` 0.7 直连 + rayon runner（**默认**，§12.8 全场最快，BSD-3）；
  - `jxl-rs-1t` = `jxl-image-rs-integration` 官方 image hook（单线程，对照/回退）；
  - `jxl-oxide` = jxl-oxide 0.12（慢 10×，对照）。
  - feature 可叠加，叠加时 `decode_dispatch` 按固定优先级 mt > 1t > oxide；
    探尺寸同理（mt/oxide 有便宜的头读取，1t 退回全解码）。
  - GPL 的 libjxl 对照**只留在探针**（`--features jxl-probe,jxl-probe-libjxl`），
    不进本模块（本 crate MIT）。
- **`windcore` 侧**（`rust/Cargo.toml`）：`rossi_local_core` 以
  `default-features = false, features = ["avif"]` 依赖，JXL 后端由 windcore 自己的
  `[features]` **透传**：`default = ["jxl-rs-mt"]`，另有 `jxl-rs-1t` / `jxl-oxide`。
  **切换 App 的 JXL 后端 = 改 windcore default 一行 + 重编**，Flutter 侧零改动。
- **归属联动**：`page_order::JXL_CORE`（`cfg!` 常量）—— 任一后端 feature 开着，
  `.jxl` 页从外壳档进核心档（`decode_support` 先判 jxl 再查常量表），
  `decode()` 按魔数分流（`FF 0A` 裸流 / ISOBMFF 容器两种都认），
  `probe_size` 走 `jxl_backend` 的便宜头读取（`image` 的 guess 不认识 JXL）。
- **测试**：`cargo test -p rossi_local_core` 默认 feature 57 passed；外壳样例
  回归线从 jxl 换成 heic（jxl 开 feature 后不再是外壳档）。探针 `scale_probe`
  改为复用 `jxl_backend` 模块（消掉重复实现），GPL 对照仍留在探针内。
- **没做**：JXL 的 DCT 缩档（§12.8 第 5 点）、多帧/动画页（漫画用不到）。
